### 5. Finish the Analytics tab

In flight as of writing: `Dashboard.tsx` has the imports and `useAccentSync`
now returns the accent string, but `AnalyticsTab` is still the placeholder
`<ul className="plan">`. Everything it needs is built and committed in
`deeb0a4` — one SQL aggregation, four charts, two heatmaps, 103 passing
assertions.

**Acceptance criteria, each of which is a charter rule rather than taste:**

- **A null payload says so.** `analytics.get()` resolving to null means the
  read failed. Render that as a failure. A zeroed payload reads as "you have
  never worked", which is both false and alarming.
- **`.panel--wide`.** `.panel` caps at 900 px, a reading width; the Data tab
  already opts out and the charts are worse off inside it.
- **The time-of-day heatmap states its range and its row count, and uses
  app-recorded rows only.** It currently has **3 rows** to work with — every
  imported row has a null `started_at`, because a countdown reading cannot
  become a clock time. That caveat is load-bearing, not boilerplate, and the
  chart should look honestly empty rather than quietly misleading.
- **Rate trends are scoped to one unit and the UI names it.** Words per minute
  and questions per minute are different quantities; they are never charted,
  averaged or trended together.
- **The pace chart plots the ratio**, never absolute target against actual.
  `250 words` and `19 questions` on a shared axis is the same category error as
  trending rates across units. `PacePoint.ratio` exists for this.

  Note on how this item moved, because it moved twice. The criterion was
  originally vacuous - `analytics.pace` is computed and consumed by nothing, so
  there was no chart for it to be true of, and I wrote it without checking.
  I then ruled not to build one today, on the grounds that an empty seventh box
  is worse than no chart. **The user overruled that and was right.** A chart
  that hides until it has data cannot teach anyone the feature exists: you
  would have to already know the pace loop is recorded before you would ever
  see the chart proving it. An empty state is a prompt; a missing chart is
  invisible. And the ruling was internally inconsistent - the same tab already
  renders a time-of-day heatmap on three rows with an honest caption, which is
  exactly the pattern being refused here.

  **Build it**, with a designed empty state rather than a blank box, saying
  what fills it: set a pace target on a timer and the session is recorded
  against it. Be straight that imported history cannot contribute - no
  imported row carries a pace target and none ever will - so this one fills in
  from use rather than from the 3.5 years already in the database.
- **Unlabelled renders deliberately.** After item 1 there is a real row with a
  null `project_id`. It must read as "Unlabelled" in both Analytics and Data,
  not as a blank, and the Data tab's `projectId: -1` filter must find it.
- **Averages run over calendar days in the range, not active days.**

**Done when:** screenshots exist, taken with `npm run shoot` against the real

### 8. ~~Ring-mode header icons~~ — the harness, not the CSS. Implementer owns.

**Struck and rewritten 2026-11-05. The original item was wrong and the error
was mine**, so the original text is kept here rather than quietly replaced:

> `.card.is-ring .card__head` computes to `opacity: 0` and the six icons paint
> anyway, because `backdrop-filter: blur(8px)` on `.card.is-ring .tools`
> establishes its own stacking context and samples the backdrop independently
> of the ancestor's opacity group.

That mechanism is impossible. `main.css:640` does set `blur(8px)` on
`.card.is-ring .tools`, but `main.css:732` overrides the same selectors to
`backdrop-filter: none` under "controls as bare icons", later in the file and
therefore winning. Measured on the live page, every header icon reports
`backdropFilter: "none"`, with no `filter`, `mix-blend`, `isolation`,
`will-change` or `contain` anywhere on the chain to `body`. I wrote the claim
into this spec from a previous session's report without checking it.

**The ring-mode CSS is correct.** On a composited window with real pointer
events: at rest `opacity: 0` and no icons painted; pointer over the ring gives
`opacity: 1` and all six; `elementFromPoint` gives drag on the ring stroke and
the dial interior, no-drag on the header band. No markup was moved, so the
drag-region rule was never in play.

**The real defect is in `scripts/shoot.ts`.** Reported by the artist session
with measurements; recorded here as their measurement and method, not as
settled fact, because nobody has yet reproduced it independently.

A `show: false` BrowserWindow is never composited, so Chromium never ticks its
animation clock. `shoot.ts` reaches ring mode by clicking the variant toggle,
which applies `.is-ring` at runtime and starts the 160 ms opacity transition at
`main.css:605-615` running 1 to 0. The transition stays pinned on frame zero
however long the harness waits - still 1 after 600 ms - `capturePage()`
composites that frozen frame, and the clock only catches up afterwards, which
is why reading opacity immediately after the capture returns 0. A
capture / wait 400 ms / capture again produced correctly hidden icons.

Bar mode photographs correctly in the same run, and that asymmetry is the
strongest part of the account: bar hides its chrome with a static `opacity: 0`
from first paint, so no transition runs and there is no frame to freeze. It
predicts which shots break and which do not.

**This invalidates screenshot evidence for item 5 as well**, and that is the
part that matters. Every shot whose drive script changes state before capturing
is affected: `timer-pace-panel`, `pace-window`, `timer-bar-hover` and all four
dashboard tabs. **Recharts animates on mount by default**, so a frozen clock
renders series at frame zero - flat, empty or zero-height. `shoot.ts`'s own
note on `dash-analytics-tall` already lists "an empty series" among the faults
it exists to catch; that may be the harness rather than the chart. Not yet
confirmed either way.

**Done when:** the first capture is discarded (or the page is settled some
other way); the Analytics tab is re-shot and compared against the previous
pair; and **any chart change made because a screenshot looked empty or flat is
revisited**, since it may have been fixing something that was never wrong. Say
plainly if the charts were fine all along - that is a result worth recording,
not a non-event.

**And one thing nobody has checked:** the installed build as the user runs it,
in ring mode, at rest. Both the original claim and its refutation came from
harnesses. Thirty seconds of looking at the real window during the item 7
reinstall closes it. This component has now produced three real bugs and one
phantom, and the user films it.

### 11. A session that fails to record says nothing, and the stop prompt accepts input into the void. Implementer owns.

Found in the item 9 branch review, 2026-11-05. This is the failure the whole
project is built to avoid, and the channel that was designed to report it was
never wired up.

**The chain, traced end to end:**

1. `recordSession` throws — a locked database, a damaged page, anything.
   `main/index.ts:296` catches it correctly, so the timer still stops cleanly
   and Electron does not raise a crash dialog. That part works and the comment
   above it explains why it matters.
2. It sends `timer:recordFailed` to the window. **Nothing receives it.**
   `grep -rn "recordFailed" src/` returns exactly one hit, the send itself.
   `preload/index.ts` exposes no `onRecordFailed`, and `App.tsx` subscribes to
   `onUpdate` and `onExpired` only.
3. `instance.lastCompleted` is set to `null`.
4. `timer:completed` is sent anyway, so the stop prompt opens looking normal.
5. The user types `19` and `questions`. `saveQuantity` invokes
   `sessions:setQuantity`, whose handler is
   `const completed = instanceFor(event)?.lastCompleted; if (completed) ...` —
   so with `lastCompleted` null it **does nothing and returns successfully**.
6. A one-click stop reason does the same nothing.
7. The prompt auto-dismisses after 30 seconds.

The user has just watched a session end, labelled its output, and lost all of
it, with no error anywhere on screen. The session is gone and so is everything
they typed about it.

**`CLAUDE.md` currently claims this is handled** — "A failure is logged and
sent to the window as `timer:recordFailed`". It is sent. It is sent to nobody.
A spec that quietly disagrees with the build is the thing that document opens
by warning against.

**Compounding it: 28 `void window.api...` calls in `App.tsx` and zero
`.catch`.** `void` silences the floating-promise lint; it does not handle a
rejection. So even when `lastCompleted` exists, a `setQuantity` that rejects
mid-type is silent. The doc comment on `saveQuantity` says "There is no moment
where what is on screen is not what is stored, so dismissing the prompt can
never lose an entry" — which is exactly the guarantee that is being broken.
This is the same shape as the import bug `CLAUDE.md` already records: a
rejected invoke that left a button disabled forever and said nothing.

**Done when:**

- `preload` exposes `onRecordFailed`, and the timer window shows it. It needs
  to be visible and to persist rather than auto-dismiss — this is the one
  message the user must not miss, and the window is 250px, so it likely
  replaces the stop prompt rather than sitting beside it.
- **The stop prompt does not open when there is nothing to attach to.** Asking
  for a quantity that cannot be stored is worse than asking for nothing. Either
  suppress it on failure, or open it in an explicit error state.
- The writes that carry user data — `setQuantity`, `setStopReason`, `undoStop`
  — handle rejection and surface it. The other 25 invokes are navigation and
  window operations where failure is self-evident; they do not all need
  wrapping, and blanket-wrapping them would bury the three that matter.
- A test that makes `recordSession` throw and asserts the window says so.
  `scripts/` already has the pattern, and this is reachable by pointing the
  harness at a read-only database file.

**Not fixed by the manager because** it is renderer logic plus a visible
treatment, which is the implementer's column with a CSS edge the artist may
want. The main-process half already does the right thing and needs no change.

### 12. The Analytics tab is a motivational instrument, not only a report. Artist leads, implementer on logic.

The user's framing, 2026-11-05, and it is a correction to how all three sessions
have been building: **"this app is supposed to be as much analytical as it is a
psychological thing to keep me, the user, motivated."** Opening the tab should
feel like progress, not like an audit.

This is a standing design constraint, not one change. When a panel can be
honest in two ways, prefer the one that shows movement.

**12a. Remove the streak counter.** The tile reads `60 · best streak ·
current 0`, which says: your best was months ago and today you have nothing.
It is the clearest example of the whole problem.

Note the contradiction and do not let it be re-added: `PROJECT_PLAN.md`
Phase 4 lists "Consistency and streaks — days worked, gaps, current and best
streak" as confirmed wanted. **The user has overruled their own earlier
request.** That line is being struck in the same change so a future session
does not reinstate the tile from the plan.

`streaks()` in `shared/analytics.ts` stays — it is pure and covered by the
103-assertion harness — but nothing renders it. If consistency returns it must
be in a form that cannot report a zero as its headline.

**12b. Week-over-week compares hours per active day, not totals.** The user's
reasoning is right: comparing a 5-day week's total against a 7-day week's total
punishes the shape of the week rather than the work in it.

Measured on the real history, for the week ending 2026-11-05:

| | total | active days | per active day |
| --- | --- | --- | --- |
| this week | 18.6 h | 5 | 3.7 h |
| last week | 37.9 h | 7 | 5.4 h |
| **change** | **−51%** | | **−31%** |

So the fairer metric is still negative, and **this is where the brief has to be
taken literally rather than generously**. No ratio turns a lighter week into a
heavier one, and one that did would be lying — the user has said this data
informs real decisions, so a flattering number is worse than a discouraging
one. Note also that two of this week's seven days are days the app was not
usable, which is our outage showing up in their statistics.

The fix is therefore **what occupies the headline slot**, not which ratio is
printed. Per-active-day because it is fairer; demoted from the hero tile
because a comparison can always go down. The hero slot wants a figure that is
monotonic or forward-looking — hours this month, hours since the first
session, sessions logged, a personal best stated without a "current" beside it.
Totals that only ever grow are honest *and* encouraging, which is the
combination to reach for.


**12c. What "fair" turned out to mean, measured.** The user accepted a negative
number and asked only that the comparison be fair. Three framings, on the real
history at 2026-11-05:

| window | total | active days | per active day |
| --- | --- | --- | --- |
| ends **today** (what ships now) | −51% | 5 vs 7 | **−31%** |
| ends **yesterday**, the last complete day | −37% | 6 vs 6 | **−37%** |
| ends at the last day with any work (11-03) | −27% | 7 vs 6 | **−38%** |

Two things fall out, and the first is the uncomfortable one.

**Fairness makes the number worse, not better.** The −31% was the flattered
figure: today contributes no hours and so is excluded from the denominator,
while the week before had seven active days. Once the windows are comparable
the answer is −37%, and it holds at −38% under a third framing. The real signal
is stable and is not an artefact of week shape: roughly the same number of
working days, about 3.6 h on each against 5.8 h before. Report that.

**So: end the window at the last complete day, and compare hours per active
day.** Both corrections are principled rather than chosen for their answer —
a day still in progress is not a data point, and a week with fewer working days
should not be penalised for its shape. They happen to agree at −37%, which is
the sign they are measuring the same thing.

**12d. And the comparison must say when it cannot be trusted.** The deeper
unfairness is not the metric. Every row in the database arrived by import, the
most recent is **2026-11-03**, and the window runs to today — so a
partially-logged week is being compared against a fully-logged one, and no
choice of ratio fixes that.

When the most recent session predates the window, a week-over-week figure is
measuring how stale the import is, not how much work happened. The tile should
say so — *no sessions logged since 3 November* — rather than print a decline.
This resolves itself the moment the app is in daily use, which is exactly why
it must not display a discouraging number in the meantime for a drop the user
did not cause: the app was unusable for most of the period it is reporting on.

**Done when:** no tile can report a zero or a loss as its headline figure; the
week comparison is per active day and is secondary; and the tab opens on
something that went up.

### 13. The Analytics tab is customisable. Artist leads layout, implementer and manager on persistence.

Asked for directly: **drag panels into a different order, change the font size,
hide panels and show them again.**

- **Order, visibility and font scale persist**, so the arrangement is the
  user's rather than a session's. `app_settings` already exists for exactly
  this — key/value that survives a restart — and is the right home. One key
  holding a JSON layout is fine; it is a preference, not a record.
- **A hidden panel must be findable again.** The failure to avoid is the Data
  tab's: a fixed cap that silently hides the rest and leaves no way back.
  Whatever hides a panel has to be reversible from somewhere obvious.
- **Font scale applies to the tab**, not the app, unless the user asks
  otherwise. The timer window is filmed and its type is tuned to 250px.
- **Dragging must not fight the drag regions.** This is the dashboard, not the
  timer window, so `-webkit-app-region` is not in play — but check before
  assuming, because that assumption has broken this project three times.
- **Default to the current layout.** A user who touches nothing should see
  exactly what they see now, including the hero calendar.


**13a. The stored shape, settled 2026-11-05.** The implementer asked before
building, which was right — a schema is the expensive thing to change once a
user's row exists.

One key in `app_settings`, `analytics.layout`, holding JSON:

```json
{ "v": 1, "order": ["calendar", "hours", "projects"], "hidden": ["timeOfDay"], "fontScale": 1 }
```

**Order and hidden are separate, not one list with holes.** Their argument and
it is correct: a panel hidden and then restored has to come back *where it
was*, and an order with gaps in it cannot express a position that is currently
empty. `order` is every panel the user has an opinion about; `hidden` is a set
of ids drawn from it.

Three rules that keep it working across versions, because this file outlives
the panel list:

- **An id in `order` that no longer exists is ignored.** A removed panel must
  not strand the layout or throw.
- **A panel not in `order` is appended in its default position and shown.**
  This is what makes a *new* panel appear for an existing user. A stored layout
  is a record of preferences expressed, not a complete list of what exists, and
  treating it as the latter means every future panel is invisible to everyone
  who ever dragged anything.
- **Unparseable or absent means defaults**, silently. A corrupt preference is
  not worth an error dialog in front of a chart.

`v` is there so a future shape change can be detected rather than guessed at.
`fontScale` rides in the same object because it is the same kind of thing and
one key is one write; it is a number so it can be clamped rather than a named
size that needs a lookup.

Writing goes through `setSetting`, which checkpoints via `checkpointSoon()`
since `a50b183` — so a layout change is durable within about a second and
survives the kind of loss that took the history in September.

Deliberately not specified here: the control surface. Whether that is a drag
handle per panel, an edit mode, or a settings list is the artist's call, and
the honest empty states and paired panels they have already built are the
reason to leave it with them.

### 14. Finishing the output entry must confirm the write and close the strip. Implementer owns logic, artist the treatment.

Asked for by the user on 2026-11-05 after their first real session on the app
— which recorded correctly: id 2478, "Editing", 574 s, `8 seconds edited`,
`finished_early`. Their words: *"when i finish entering the output there is
something that confirms that my data was added, and the menu to insert how
much work i did goes away."*

**The gap, traced.** `saveQuantity` writes as the user types, which is right
and stays. `holdStopPrompt` cancels the 30-second auto-dismiss the moment
either field is focused, which is also right — a prompt that vanishes
mid-word is one you stop bothering with. But the only two things that close
the strip are `answerStop` (picking a stop reason) and `undoStop`. So a user
who records output and does **not** pick a reason has no way to finish: the
strip stays until the window does, and nothing ever says the quantity landed.

Stop reasons are explicitly optional and skippable — about 75% of sessions
end early and a mandatory prompt would stop the logging happening — so the
path with no reason is the common one, not an edge case.

**What to build.**

- **A confirm control, and it is a checkmark rather than an X.** Exactly the
  pace panel's reasoning, already settled in `CLAUDE.md`: values apply as they
  are typed, so the control confirms rather than dismisses. Reuse that
  treatment so the two read as the same gesture.
- **Enter confirms, and walks the fields first.** Also the pace panel's
  pattern: Enter in quantity moves to unit, Enter in unit confirms and closes.
  A session can then be stopped and its output recorded without the mouse.
- **The confirmation must be of the write, not of the keypress.** This is the
  part that matters and the part the day argued for. The quantity is already
  written as it is typed, so a checkmark that merely closes would be
  confirming a keystroke. On confirm, wait for the outstanding
  `setQuantity` to resolve, and only then say so. If it rejects, show the
  failure and **do not close** — the user is still looking at the only copy of
  what they typed.
- **Say what was stored, not that something happened.** "Saved · 8 seconds
  edited" tells them the number and the unit that landed; "Saved" alone is the
  same claim their typing already made. Then close, after about a second.
- **Closing by reason still works and should also confirm.** Picking a stop
  reason already closes the strip; it should carry the same confirmation,
  since it is writing a reason as well as whatever quantity is in the fields.

**Done when:** entering a quantity and pressing Enter (or the checkmark)
shows what was stored and closes the strip; a failed write says so and keeps
it open; no reason is required at any point; and the 30-second auto-dismiss
still applies when the fields are never touched.

**Verify by pressing the button**, not by reading the handler — `npm run
build` first, since `shoot` renders `out/`. The check that matters is the
failure path: make `setQuantity` reject and confirm the strip stays open with
the error, because that is the case where the user's only copy of the number
is on screen.

## Standing constraints

The ones that have each already cost something here:

1. **Never write to `Roaming\deep-work-tracker` without taking a copy first.**
   It is the user's real history. Imports, restores and repairs go to the
   manager.
2. **Never run the packaged app to test.** `npm run dev` resolves to the dev
   profile; the installed app owns the real data.
3. **Never force-kill the app.** See item 7.
4. **Check the drag-region rule before writing JSX that overlays a dial.**
5. **Say which file you are taking before you edit it.** Three sessions share
   one checkout. Last night two of us edited `backup.ts` at once and briefly
   broke the build, because I flagged a bug to the implementer and then fixed
   it myself without saying so. Stage by path; never `git add -A`.
6. **Evidence, not assertion.** Query a copy of the database rather than
   trusting a tool's own report, and screenshot the UI rather than reasoning
   about the markup. Both have caught things review missed, tonight included.

## One thing that is settled, so it does not get reopened

`streaks()` filters days on `hours > 0`, so a day whose only session recorded
zero running seconds does not count as worked. I had suggested `sessions > 0`
instead; the implementer encoded the opposite in a named test, and on reflection
that is the better call — a zero-second row is a misclick, not a day's work. The
3 app rows in the database run 2–8 seconds, so they are unaffected either way.
Left here because an undocumented decision is one that gets re-litigated.
